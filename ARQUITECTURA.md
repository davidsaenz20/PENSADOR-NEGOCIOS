# ARQUITECTURA — PENSADOR-NEGOCIOS

Definición de la arquitectura funcional del sistema.

---

# 1. PROPÓSITO

Este documento define cómo funciona PENSADOR-NEGOCIOS como sistema de pensamiento.

No define todavía:

- código;
- APIs;
- automatizaciones;
- interfaz;
- base de datos;
- infraestructura técnica.

Define el proceso lógico que deberá seguir el sistema cuando sea utilizado desde ChatGPT.

---

# 2. PRINCIPIO GENERAL

PENSADOR-NEGOCIOS funciona como un proceso iterativo de descubrimiento, investigación, ataque y evolución de oportunidades.

Flujo conceptual:

ENTRADA
→ EXPLORACIÓN
→ DESCUBRIMIENTO
→ INVESTIGACIÓN
→ FORMULACIÓN
→ CONTRASTE
→ ATAQUE
→ EVOLUCIÓN
→ PRIORIZACIÓN
→ DECISIÓN

El flujo no es estrictamente lineal.

Una fase puede provocar el regreso a una fase anterior.

---

# 3. ENTRADAS DEL SISTEMA

El sistema debe poder comenzar desde diferentes situaciones.

## 3.1. EXPLORACIÓN LIBRE

Entrada aproximada:

"Busca una oportunidad de negocio."

El sistema decide qué investigar.

No debe generar una idea inmediatamente.

Debe iniciar un proceso de descubrimiento.

---

## 3.2. EXPLORACIÓN DIRIGIDA

El usuario proporciona uno o varios criterios.

Ejemplos:

- sector;
- nicho;
- país;
- cliente;
- presupuesto;
- tecnología;
- conocimientos;
- modelo de negocio;
- B2B;
- B2C;
- ingresos recurrentes;
- bajo coste inicial;
- automatización;
- tiempo disponible.

El sistema utiliza estas restricciones como contexto de búsqueda.

No deben impedir detectar oportunidades inesperadas cuando sean relevantes.

---

## 3.3. IDEA EXISTENTE

El usuario proporciona una idea.

El sistema debe tratarla inicialmente como:

**HIPÓTESIS**

Nunca como conclusión.

Debe investigarla y tratar de:

- comprobar existencia;
- descubrir competidores;
- encontrar alternativas;
- detectar debilidades;
- identificar oportunidades;
- diferenciarla;
- modificarla;
- atacarla.

---

# 4. FASE 0 — DEFINICIÓN DEL OBJETIVO

Antes de investigar, el sistema debe determinar qué está buscando.

Debe conocer, cuando sea relevante:

- tipo de exploración;
- restricciones;
- recursos;
- preferencias;
- horizonte temporal;
- objetivo económico;
- tolerancia a complejidad;
- conocimientos disponibles.

Si el usuario no proporciona restricciones suficientes, el sistema puede comenzar con exploración abierta.

No debe bloquearse innecesariamente solicitando información que no sea imprescindible.

---

# 5. FASE 1 — EXPLORACIÓN

Objetivo:

Encontrar zonas donde puedan existir oportunidades.

El sistema puede explorar:

- problemas;
- mercados;
- comportamientos;
- cambios;
- tecnologías;
- regulaciones;
- tendencias;
- ineficiencias;
- quejas;
- tareas repetitivas;
- procesos manuales;
- necesidades insatisfechas.

No debe intentar encontrar inmediatamente "el negocio".

Debe construir un mapa inicial de posibilidades.

---

# 6. FASE 2 — DESCUBRIMIENTO DE PROBLEMAS

Objetivo:

Identificar problemas concretos.

Cada problema debe intentar describirse mediante:

- quién lo sufre;
- qué ocurre;
- cuándo ocurre;
- con qué frecuencia;
- qué consecuencias produce;
- cómo se resuelve actualmente;
- cuánto cuesta;
- qué frustración genera;
- por qué las soluciones actuales no son suficientes.

El problema debe ser suficientemente concreto para poder investigarse.

---

# 7. FASE 3 — INVESTIGACIÓN DE SOLUCIONES EXISTENTES

Objetivo:

Determinar cómo se resuelve actualmente el problema.

Debe buscar:

- competidores directos;
- competidores indirectos;
- sustitutos;
- herramientas;
- servicios;
- procesos manuales;
- soluciones internas;
- hojas de cálculo;
- marketplaces;
- agencias;
- profesionales;
- productos generalistas.

La investigación no debe limitarse a buscar exactamente la solución imaginada.

---

# 8. FASE 4 — DETECCIÓN DE OPORTUNIDADES

A partir de los problemas y de la investigación, el sistema debe buscar:

- necesidades insuficientemente atendidas;
- segmentos ignorados;
- soluciones deficientes;
- procesos excesivamente caros;
- procesos excesivamente manuales;
- mercados fragmentados;
- problemas nuevos;
- nuevas posibilidades tecnológicas;
- cambios de comportamiento;
- cambios regulatorios;
- combinaciones interesantes.

Resultado:

Una o varias oportunidades potenciales.

---

# 9. FASE 5 — FORMULACIÓN DE HIPÓTESIS

Cada oportunidad debe convertirse en una hipótesis explícita.

Formato conceptual:

"Creemos que [cliente] tiene [problema] y que podría pagar por [solución] porque [motivo]."

La hipótesis debe poder investigarse.

---

# 10. FASE 6 — INVESTIGACIÓN DE LA HIPÓTESIS

El sistema debe intentar obtener evidencia a favor y en contra.

Debe investigar:

- existencia del problema;
- intensidad;
- frecuencia;
- soluciones actuales;
- competencia;
- clientes;
- precios;
- comportamiento;
- demanda;
- distribución;
- barreras;
- regulación;
- tecnología;
- modelos similares.

No debe detenerse en la primera confirmación.

---

# 11. FASE 7 — ANÁLISIS DE NOVEDAD Y DIFERENCIACIÓN

El sistema debe determinar:

### Existencia

¿Existe algo similar?

### Diferenciación

¿Qué cambia?

### Ventaja

¿Por qué alguien elegiría la nueva solución?

### Saturación

¿Cuántas alternativas existen?

### Espacio

¿Qué queda sin resolver?

La conclusión debe distinguir entre:

- inexistente;
- existente;
- existente pero mal resuelto;
- existente pero dirigido a otro segmento;
- existente pero con otro modelo;
- existente pero con una oportunidad de diferenciación.

---

# 12. FASE 8 — ATAQUE

Esta fase es obligatoria para las oportunidades que avancen suficientemente.

Objetivo:

Intentar demostrar que la oportunidad no merece la pena.

Preguntas:

- ¿Por qué fracasaría?
- ¿Por qué nadie pagaría?
- ¿Qué alternativa ya resuelve el problema?
- ¿Qué competidor podría copiarlo?
- ¿Qué barrera existe?
- ¿Qué coste tendría adquirir clientes?
- ¿Qué podría impedir la distribución?
- ¿Qué regulación puede afectar?
- ¿Qué dependencia tecnológica existe?
- ¿Qué supuesto podría estar equivocado?

Resultado posible:

- sobrevive;
- sobrevive parcialmente;
- necesita pivotar;
- debe investigarse más;
- debe descartarse.

---

# 13. FASE 9 — EVOLUCIÓN

Si una oportunidad presenta potencial pero contiene debilidades, el sistema debe intentar modificarla.

Puede cambiar:

- cliente;
- problema;
- solución;
- nicho;
- precio;
- modelo;
- canal;
- tecnología;
- distribución;
- alcance.

También puede combinarla con otra oportunidad.

Resultado:

Nueva hipótesis.

La nueva hipótesis vuelve al proceso de investigación.

---

# 14. FASE 10 — PRIORIZACIÓN

Cuando existan varias oportunidades suficientemente investigadas, deben compararse.

La comparación debe considerar, como mínimo:

- fuerza del problema;
- evidencia;
- diferenciación;
- novedad;
- competencia;
- disposición potencial a pagar;
- dificultad;
- distribución;
- potencial económico;
- capacidad de prueba;
- incertidumbre.

Los criterios exactos y su importancia podrán evolucionar durante las pruebas reales.

No se establece todavía una fórmula matemática obligatoria.

---

# 15. FASE 11 — DECISIÓN

Una oportunidad debe terminar en una decisión explícita.

Estados posibles:

### DESCARTAR

La evidencia acumulada indica que no merece continuar.

### PAUSAR

La oportunidad es interesante pero falta información.

### INVESTIGAR

Existe suficiente potencial para continuar investigando.

### PIVOTAR

Existe una oportunidad, pero la hipótesis actual necesita cambios.

### COMPARAR

Debe compararse con otras oportunidades.

### CANDIDATA

Ha superado las principales fases de investigación y merece consideración seria.

### PASAR A BASE-PROYECTOS

La oportunidad está suficientemente madura para estudiar su construcción como proyecto real.

---

# 16. BUCLES DE RETROALIMENTACIÓN

El sistema debe poder retroceder.

Ejemplos:

INVESTIGACIÓN
→ descubre que el problema no es importante
→ DESCUBRIMIENTO DE PROBLEMAS

INVESTIGACIÓN
→ descubre un competidor inesperado
→ DETECCIÓN DE OPORTUNIDADES

ATAQUE
→ encuentra una debilidad
→ EVOLUCIÓN

EVOLUCIÓN
→ genera una nueva solución
→ INVESTIGACIÓN

PRIORIZACIÓN
→ aparece una incertidumbre importante
→ INVESTIGACIÓN

La arquitectura debe permitir estos ciclos.

# 18. PRINCIPIO DE NO LINEALIDAD

El sistema no debe tratar las fases como una lista rígida.

Una investigación puede revelar un problema completamente diferente.

Una oportunidad puede generar otra.

Una idea descartada puede producir una nueva oportunidad.

El sistema debe permitir abandonar temporalmente una línea de investigación y seguir otra.

---

# 19. INVESTIGACIÓN COMO MOTOR CENTRAL

La investigación no es una fase secundaria.

Es uno de los motores principales del sistema.

El objetivo no es utilizar investigación para justificar ideas.

El objetivo es permitir que la investigación cambie las ideas.

---

# 20. DIFERENCIA ENTRE DESCUBRIMIENTO Y GENERACIÓN

El sistema debe diferenciar:

## DESCUBRIR

Encontrar un problema, necesidad, comportamiento, cambio o ineficiencia que ya existe.

## GENERAR

Proponer una posible solución o modelo de negocio.

El sistema debe intentar descubrir antes de generar cuando la situación lo permita.

---

# 21. SALIDA DE UNA SESIÓN

Una sesión puede producir:

- ninguna oportunidad;
- una oportunidad;
- varias oportunidades;
- una hipótesis;
- una idea evolucionada;
- una oportunidad descartada;
- un nuevo problema;
- una investigación pendiente;
- una candidata para construcción.

No existe obligación de terminar con una idea de negocio.

---

# 22. CONTINUIDAD

Las investigaciones importantes deben poder continuar posteriormente.

El sistema debe poder conservar:

- problema;
- hipótesis;
- evidencia;
- fuentes;
- competidores;
- objeciones;
- decisiones;
- pivotes;
- descartes;
- preguntas pendientes.

La forma concreta de conservar esta información se definirá posteriormente.

---

# 23. FUTURA CONEXIÓN CON BASE-PROYECTOS

Cuando una oportunidad alcance el estado:

**PASAR A BASE-PROYECTOS**

deberá poder convertirse en una entrada para el sistema metodológico de BASE-PROYECTOS.

La transferencia deberá contener, como mínimo:

- problema;
- cliente;
- oportunidad;
- solución propuesta;
- evidencia;
- competencia;
- diferenciación;
- riesgos;
- incertidumbres;
- hipótesis pendientes;
- motivo por el que merece ser construida.

---

# 24. ESTADO DE LA ARQUITECTURA

**Versión:** 0.1

**Estado:** Diseño inicial

Esta arquitectura es una hipótesis de funcionamiento.

Deberá modificarse cuando las pruebas reales demuestren que una fase:

- sobra;
- falta;
- está mal situada;
- produce resultados deficientes;
- es demasiado compleja;
- o puede simplificarse.

---

# 25. PRINCIPIO FINAL

El sistema no debe avanzar porque haya terminado una lista de pasos.

Debe avanzar porque la evidencia obtenida permita justificar el siguiente paso.

La pregunta central en cada transición debe ser:

> "¿Qué hemos aprendido y qué deberíamos hacer ahora como consecuencia de ello?"
